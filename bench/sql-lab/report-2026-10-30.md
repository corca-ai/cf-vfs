# SQL lab — where reading a large wiki spends its time, 2026-10-30

The SQL lab Worker (`eval/sql-lab`, `lab.vfs.borca.ai`, deployed with
`npm run deploy:lab`) holds Durable Objects with the real cf-vfs schema,
seeded through `SqlFileSystem.writeFiles`, and runs arbitrary statements or
filesystem reads in them, so a query design is measured where it will run
without a deploy per idea. `lab.mjs` is the client. Timings are taken at the
Worker around one request and divided by the request's `repeat`; the object's
own clock stands still during synchronous SQL. An empty request costs about
20 ms. Exploration only: adopting a query still follows the performance
protocol.

Lab `wiki10k` held the 10,000-page S3 wiki (49.7 MB) under `/wiki`. Single
runs of three requests each unless noted (`experiments-2026-10-30-wiki10k.log`,
`read-path-2026-10-30.log`).

| What | Time |
| --- | ---: |
| fixed cost of a statement (`SELECT 1`, path lookup by index) | 0.015–0.017 ms |
| `stat` through the filesystem, per page | 0.14–0.22 ms |
| `readFile` then cancel, per page | 0.34–0.39 ms |
| `readFile` and consume the stream, per page | 0.40–0.48 ms |
| one body by path in its own statement | 0.089 ms |
| all 10,000 pages through `readFile`, one at a time | 4.0–5.7 s |
| all 10,000 bodies in one range scan | 0.34 s |
| all 10,000 bodies in 64-path batches (estimate from 10 batches) | about 1.0 s |
| substring search over every body inside SQLite (`instr`, `LIKE`) | 0.65–0.95 s |
| FTS5: build an index over every body / one `MATCH` query | 2.7 s / about 0.25 ms |

Durable Object SQLite binds at most 100 parameters, so batches of paths stay
at 64, as `statMany` already does.

What this says:

- SQLite is not what is slow. It scans the 50 MB of bodies in a third of a
  second and runs a statement in 15 µs.
- The filesystem's per-call work is (refined below: mostly crossings into the
  runtime, such as a stream per file, rather than JavaScript). A `stat` costs about eight times
  the SQL lookup behind it and a `readFile` about four times the SQL read of
  the same body, so a command that opens every page (`grep -r`, an awiki first
  run, `cat` over a glob) spends 4–6 s of a 10,000-page wiki on per-file
  overhead. Locally the same reads take 0.012 ms per page, so the cost is
  specific to the Workers runtime.
- Moving the bulk paths into SQL would cut that by 5–15 times: one scan or a
  few dozen batched statements instead of a call per page, and substring
  prefiltering inside SQLite instead of in JavaScript.
- FTS5 is available. An index would answer repeated searches in under a
  millisecond, at the cost of keeping it current on every write.

## Where the per-file cost actually goes, and bulk reads

Later the same day (`micro-2026-10-30.mjs`, `entry-columns-2026-10-30.mjs`,
`bulk-read-2026-10-30.mjs`; logs and JSON beside them). The lab gained fixed
runtime microbenchmarks, `readMany` read modes and a shell endpoint that runs
a script in a fresh evaluation shell, with bulk reads offered or withheld.

The "per-call JavaScript" above is mostly crossings into the runtime, not
JavaScript. Ordinary code runs about five times slower in a Durable Object
than on the development machine; operations that cross into workerd run 30 to
130 times slower (medians of five requests, minus an empty request):

| Operation | Workers | Node (local) |
| --- | ---: | ---: |
| a function call, an `await`, a clock read | 0.08–0.12 µs | 0.013–0.023 µs |
| an async generator step | 0.29 µs | 0.07 µs |
| add and remove an abort listener | 3.1 µs | 0.09 µs |
| `TextEncoder.encode` of a 200-character line | 2.2 µs | — |
| ASCII test of the same line (regular expression) | 0.07 µs | — |
| copy a 5,000-byte buffer | 16 µs | 0.4 µs |
| a byte stream of one chunk, created and drained | 144 µs | 1.1 µs |
| a default stream of one chunk | 73 µs | 0.6 µs |
| `Blob.stream()` of one chunk | 333 µs | 17 µs |

On the SQL side, per batch of 64 pages (`entry-columns`): entries as nineteen
columns 1.2 ms, as one JSON string 0.56 ms; their bodies 5.2–6.2 ms, and
`length(body)` alone 4.3 ms, so reading the body pages is itself the cost and
the shape the bytes come back in (blob, text, one concatenated text) barely
matters. That puts a floor of about 0.7–0.9 s under reading 10,000 bodies.

`readMany` (two statements per 64 paths: entries as JSON, then the admitted
bodies by id) against `readFile` one page at a time, all 10,000 pages, five
requests of 2,000 paths, three alternating trials:

| Read | Median |
| --- | ---: |
| `readFile`, stream drained | 5.0–5.9 s |
| `readMany`, each body then drained through a stream | 3.6 s |
| `readMany`, bodies used directly | 2.3 s |

Shell commands over the whole wiki, bulk reads withheld or offered, medians of
three alternating trials. v1 wrapped each bulk body in a stream; v2 passes the
chunks to `grep` directly; v3 adds `grep`'s literal rejection:

| Command | Per file | v1 | v2 | v3 |
| --- | ---: | ---: | ---: | ---: |
| `grep -rlF '[[note-0001' /wiki` (28 pages match) | 8.5–9.5 s | 6.0 s | 4.4 s | 1.7 s |
| `grep -rc '^owner:' /wiki` (every page matches) | 12.7–14.3 s | 10.3 s | 8.3 s | 6.4 s |
| `awiki lint -r` with an empty cache | 13.0–14.4 s | 5.6 s | 6.6 s | 6.9 s |

Every pair printed the same output. awiki never wrapped bulk bodies in
streams, so its v1–v3 differences are noise across sessions. Locally the same
commands take 0.3–1.0 s either way, which is why only Cloudflare could show
this. What remains for `grep -rc` is splitting 635,000 lines through async
generators; what remains for `awiki` is parsing.

the lab is a separate Worker, but deploys now wait until a benchmark cohort
ends.
