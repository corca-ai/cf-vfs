# SQL lab — where reading a large wiki spends its time, 2026-10-30

The SQL lab Worker (`eval/sql-lab`, `lab.vfs.borca.ai`, deployed with
`npm run deploy:lab`) holds Durable Objects with the real cf-vfs schema,
seeded through `SqlFileSystem.writeFiles`, and runs arbitrary statements or
filesystem reads in them, so a query design is measured where it will run
without a deploy per idea. `lab.mjs` is the client. Timings are taken at the
Worker around one request and divided by the request's `repeat`; the object's
own clock stands still during synchronous SQL. An empty request costs about
20 ms. Exploration only: adopting a query still follows the performance
protocol.

Lab `wiki10k` held the 10,000-page S3 wiki (49.7 MB) under `/wiki`. Single
runs of three requests each unless noted (`experiments-2026-10-30-wiki10k.log`,
`read-path-2026-10-30.log`).

| What | Time |
| --- | ---: |
| fixed cost of a statement (`SELECT 1`, path lookup by index) | 0.015–0.017 ms |
| `stat` through the filesystem, per page | 0.14–0.22 ms |
| `readFile` then cancel, per page | 0.34–0.39 ms |
| `readFile` and consume the stream, per page | 0.40–0.48 ms |
| one body by path in its own statement | 0.089 ms |
| all 10,000 pages through `readFile`, one at a time | 4.0–5.7 s |
| all 10,000 bodies in one range scan | 0.34 s |
| all 10,000 bodies in 64-path batches (estimate from 10 batches) | about 1.0 s |
| substring search over every body inside SQLite (`instr`, `LIKE`) | 0.65–0.95 s |
| FTS5: build an index over every body / one `MATCH` query | 2.7 s / about 0.25 ms |

Durable Object SQLite binds at most 100 parameters, so batches of paths stay
at 64, as `statMany` already does.

What this says:

- SQLite is not what is slow. It scans the 50 MB of bodies in a third of a
  second and runs a statement in 15 µs.
- The filesystem's per-call JavaScript is. A `stat` costs about eight times
  the SQL lookup behind it and a `readFile` about four times the SQL read of
  the same body, so a command that opens every page (`grep -r`, an awiki first
  run, `cat` over a glob) spends 4–6 s of a 10,000-page wiki on per-file
  overhead. Locally the same reads take 0.012 ms per page, so the cost is
  specific to the Workers runtime.
- Moving the bulk paths into SQL would cut that by 5–15 times: one scan or a
  few dozen batched statements instead of a call per page, and substring
  prefiltering inside SQLite instead of in JavaScript.
- FTS5 is available. An index would answer repeated searches in under a
  millisecond, at the cost of keeping it current on every write.
